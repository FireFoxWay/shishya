01What this is

Shishya (शिष्य — student, apprentice) is a local AI workspace. You give it documents, talk to it in plain language, and it decides how to answer: read the material, build a spreadsheet, draft a document, assemble a deck, or write and run a program. All of it happens on one laptop, inside a virtual machine whose network is off by default.

Three things it is not

  • It does not train. It reads and indexes. No weights change. Say "it reads everything you give it" — the true answer is better than the impressive one, because you can add a document and have it answered from thirty seconds later, which real training could never do.
  • It is not an autonomous agent. One decision per turn, then a known code path. A model this size left to run a multi-step loop wanders: it calls a tool, misreads the result, and three steps later is confidently doing the wrong job.
  • It is not a cloud product. There is no server. Everything is one Mac.

02The argument

Staff everywhere paste confidential records into cloud AI to get their work done. Once that leaves the building you do not control it and cannot audit it. Shishya does the same work with nothing leaving the laptop — provably, because you can switch the network off and watch it continue — and every action is written to an append-only ledger, including the ones it was refused.

The distinction that carries the pitch

Automating clerical work is crowded. The uncommon part is not the automation — it is the sandbox, the audit ledger, the network lock and the undo button. Those are an argument about how AI should be permitted to operate. Lead with those; the automation is the demonstration, not the claim.

The single best result the project has produced

Asked which suppliers a pharmacy buys most from, it discovered that KK ENTERPRISES (9,602 rows) and Kk Enterprises (1,415 rows) are the same supplier counted twice — as are PATWARI PHARMA PVT LTD and Patwari Pharma Pvt Ltd, and 24 others. Nobody asked it to look. That is the difference between doing the filing faster and being useful, and it is the story to tell.

04Architecture

Two machines on one laptop, meeting at exactly three points.

  THE MAC (host)                  │      THE SANDBOX (Lima VM, Ubuntu 24.04)
                                  │
  browser → localhost:8200        │  Xvfb :0 (1440×900) → openbox → desktop.py
        ↕                         │      ↕
  serve.py   (stdlib only)        │  18 apps: chat, findings, training, code…
        ↕                         │      ↕
  host/vm.py    → limactl         │  AT-SPI accessibility bus
  host/ledger.py → var/*.jsonl    │      ↕
  host/synth.py  → procedures     │  x11vnc :5900 → websockify :6080
        ↕                         │
  Ollama (gpt-oss:20b, GPU)       │  nftables: DROP egress except the model
                                  │
  ───────────── three crossings ──┼─────────────────────────────────────────
     :6080   the clone's screen, into an iframe on the panel
     :11434  the model, reached from inside at host.lima.internal
     virtiofs  shared/ — the only writable window between them, both ways

Why each piece sits where it does

  • The model runs on the host. Inside the VM it would fall back to emulated CPU and be far too slow to demonstrate. On the host it uses the Apple Silicon GPU.
  • The mount list is the security model. The clone cannot read ~/Documents because it is not mounted — not because code checks a path. Grant a folder by adding a line to vm/lima.yaml; revoke it by deleting the line.
  • The clone has no sudo. Even inside the sandbox the agent is unprivileged, so failures stay small and it cannot lift its own network lock.
  • The panel binds to both loopback addresses only. It can start programs inside the sandbox; bound to every interface it would be reachable by anyone on the same wifi.
  • Snapshots are APFS clones. limactl snapshot is unimplemented for the vz driver. cp -c clones a 3.2 GB disk in about four milliseconds and costs no space until blocks diverge.
  • Everything is driven from the panel. Clicking inside the sandbox has failed repeatedly; the panel reaches apps through AT-SPI and signals, which never has.

Taking things back off the clone

Files go in by being dropped on the panel. This is the way out: Take from the clone browses Work, the books, the lessons and the inbox a folder at a time, and every file is a download.

The honest starting point is that they were never trapped. shared/ is a virtiofs mount, so a report the clone wrote this morning is already on this Mac's disk — buried in a project folder nobody opens. "It is already there, in a path you have never navigated to" is not a feature anybody can use, and the browser saving it wherever the person actually keeps files is the part the mount cannot do for them.

Both directions belong in the ledger

Dropping a file wrote file.in from the first week. Nothing wrote file.out, so material leaving the sandbox left no trace at all — on a panel whose argument is that every crossing is recorded. Taking a file now logs allow file.out with its size and the folder it came from.

The containment is the same rule as everywhere else: a browser asking for a path is asking a program running on the Mac, and that program resolves it and refuses anything that is not inside the folder it was given. resolve() and a prefix test rather than a string check, because ../ is only the obvious attempt — a symlink inside shared/ pointing at the home directory would pass any amount of string inspection. Half-written .part and .tmp files are never offered: handing out a file that is still being written is the upload bug in reverse.

The shop's own books

Until the Billing app, everything here read files somebody exported from somewhere else. The counter produces the shop's data as it happens — two plain CSVs under shared/billing/, seeded on first run from whatever inventory is in the material folder, so it opens stocked rather than empty:

FileWhat it holds
catalogue.csvWhat is stocked, its cost, price, stock on hand and reorder point. Rewritten whole and renamed into place, because the scheduled audit reads it while the counter is open.
sales.csvOne row per line item, append-only — for the same reason the permission ledger is. A record of takings the software can quietly rewrite is not a record of takings; a mistake is corrected by a new line.

Cost is carried on every sale line, at the cost on the day of sale. Prices change, and recomputing a month's margin from today's catalogue cost is exactly how the inventory workbook's profit became three times too good (§16). The audit sums profit; it never recomputes it.

Plain CSV on purpose: the chat, a job, a report and a person with a spreadsheet all read the same two files, and a format that needs a library to open is a format nobody can audit. The books are named separately in every model prompt, so the model is never guessing whether a row is history or this afternoon.

GST, voids and returns

Indian retail prices are quoted inclusive of tax, so price is what the customer pays and the GST inside it is price × rate ÷ (100 + rate). Storing it the other way round makes every shelf label wrong. The rate is per product, because a shop sells 0%, 5%, 12% and 18% goods on one bill and a blended rate on the total is not a legal invoice.

Nothing is ever edited or deleted. A return is a negative-quantity row naming the bill it came from; a void is one reversing row per outstanding line. A day's takings are the sum of that day's rows, and that sum is right whether or not anything was cancelled — the only property that makes a till roll worth keeping.

Voiding a bill that had already been part-returned

The first version reversed the original quantity. Return one of two and then void, and the customer was credited for three of the two they bought, with three units going back on a shelf that only ever lost two. The bill settled at minus its own value. A void now reverses only what is still outstanding, and refuses when a bill has already come back in full. Three combinations tested — plain void, part-returned then voided, fully returned then voided — all settle at exactly zero with stock back where it started.

Asking, when the answer is no

Roles say what a clerk may not do, which is half an answer. Being refused with no way to ask is how people work around software: a clerk who cannot void a mistaken bill rings up a correcting sale instead, and the books carry two wrong entries rather than one right correction.

So a refusal became a request. The clerk presses Ask to void, the head sees it under Waiting for you on the panel, and the decision is recorded — approval.granted or approval.refused, in the ledger like everything else. Approving records the decision; the app that asked performs the action and marks it done. Kept apart deliberately: a decision that half-performed something would leave the books in a state nobody asked for.

Refuses to decide twice, because a request approved twice would void a bill twice and the second would look exactly as legitimate as the first. The clerk cannot approve their own request — checked in the server, not only hidden in the panel.

Who is at the counter

Two roles, clerk and head, in shared/.role. The clerk rings up sales, prints bills and takes returns. The head additionally voids, rolls back, changes the network, snapshots, schedules, and uses the terminal.

It is not a security boundary and is never described as one. The sandbox, the mount list and the absence of sudo are the boundary; this file sits inside the very sandbox it describes. What it is for is that the person on the till should not be one slip away from cancelling yesterday's takings. The permitted list is written out rather than inferred, so adding a control means deciding who it is for.

Runs that happen with nobody there

Set in the Reports app — Every day at 18:00 · Shop audit — written to shared/.schedules.json, which the panel's scheduler re-reads every 45 seconds. Nothing is restarted and nothing is told to reload.

  • A scheduled run takes no files. Its input is the shop's books; emptying the inbox at six would steal what somebody staged that afternoon for a job they had not started.
  • Due is compared against the clock, not counted from the last run. A laptop asleep at six fires once when it wakes, late — not four times, which is what a naive interval would do.
  • The fire is logged with actor=system, which is the point: the ledger can say a thing happened that nobody asked for at that moment, and show when.

07How it decides

Each turn is one decision, then a known code path. Six actions: answer, spreadsheet, document, deck, code, clarify.

The shortcut comes first

The model reads requests well and holds a six-way choice badly. Asked twice whether "can a student with 68% attendance sit the exam" was a question, it answered clarify once and spreadsheet the other time — a question it answers well, routed first to a refusal and then to a file.

So the shapes that are unambiguous in English are settled in English, before the model is consulted:

  • Counting words (how many, total, average, most, rank…) and not a making verb → code
  • Ends in "?" or starts with can/is/does/what/which/who/how, and not a making verb → answer
  • Anything else → ask the model with a constrained JSON schema

Eight of eight test requests route as intended, and the common ones never reach the model at all.

08How it finds material

Documents are read to text, split into overlapping 1,400-character windows, indexed by term with rarity weighting. Spreadsheets additionally get a row index.

Rows are searched as rows

Prose chunking is wrong for tables. A 1,000-row sheet cut into windows hands the model fragments of unrelated rows and it blends them — asked for an HDMI cable's supplier it once returned a product id belonging to Golf Tees, with a supplier and reorder point that were never in the same row as each other. Matching rows are now returned verbatim with their header and nothing adjacent. Nine of nine facts correct on retest, zero invented.

Four rules that each took a failure to learn

  • Rarity, not every word. "reorder" and "supplier" are column headings appearing in no row; "1031" appears in exactly one.
  • Two terms must land, not one. A single coincidental "68" in an inventory dragged thirty product rows into a question about school policy.
  • Plurals fold to singular. The two-term rule immediately broke what it was meant to protect — the sheet says "Cable", the question said "cables", one term landed, every HDMI row discarded.
  • Weak passages are dropped. Anything under two fifths of the best match. Before this, a question about HDMI suppliers was handed two blocks of an unrelated macOS-vs-Windows PDF, which the model had to read and reason past — and often ran out of room doing so.

A question in another script finds the wrong document

The index is terms weighted by rarity, so a question in Telugu shares nothing with an English policy — and does not simply fail. Asked in Telugu whether a student with 68% attendance may sit the exam, retrieval returned four passages of the pharmacy inventory, because 68 is the one thing both scripts agree on. That is the §08 coincidence failure again, and the two-term rule cannot help when only one term exists.

So a question that is not in Latin script is translated for the search only. The reply is written from the original, in the language it was asked in; the translation never reaches the person and is never shown as their words. One bounded model call, and a failed translation falls back to searching with the original rather than losing the question.

The model is told the shape of a sheet

Not only column names but: which columns hold few enough distinct values to list them all (Stock Status contains only: In Stock, Low Stock), which headers are real datetimes rather than text, and which columns repeat as families (Purchased From 1..10 pairing with Purchase Qty N, which must be stacked before grouping). Each of these fixed a real failure.

09Writing and running code

The most valuable behaviour in the project

When the answer is a number, it writes a program rather than counting by eye — and shows you the program. The model is unreliable at arithmetic across rows; code that reads the file is exact. This turns the worst weakness into the most trustworthy behaviour, and it is the honest answer when anyone asks how they can know it is right.

Generated code is repaired before it runs

Three classes of slip recur, and each is cheaper to repair than to explain. All are checked against code that was already correct, so nothing valid is altered.

A program that still fails is shown its own traceback and given one attempt to correct itself. That is not always enough — shown the bracket error, the model made the identical mistake a second time, which is why the mechanical repair exists as well.

10Teaching and execution

The original thesis, and it now runs end to end.

Recording

AT-SPI events, not mouse coordinates. A step reads focused [entry] "District" in window "Applicant Registry". This is what separates it from a macro recorder, which replays coordinates and shatters when a window moves.

The finding that shaped the recorder

LibreOffice emits no text-changed event for cell entry. None. The value a clerk types into a spreadsheet — most of the job — never reaches AT-SPI. The recorder therefore watches the keyboard as well and assembles keystrokes into whole entries, held rather than logged per keystroke: eleven single-character events say far less than one step reading typed "No - below 65%" into Cell I4.

Synthesis

A trace becomes a numbered, editable, plain-language procedure. A real lesson — marking exam eligibility by hand in Calc — produced the right cells and values: I1 "Exam Eligible", I2 "Yes", I4 "No - below 65%", I9 "Principal - medical certificate".

Execution — vm/executor.py

Reads the text of each step, not the target field: the target recorded against a spreadsheet step is usually the sheet, not the cell, because that is what had focus. Four actions are supported, and they are the four the lessons actually contain:

ActionHow
goto a named cellThrough the Name Box, reached through the toolbar that owns it — it has no accessible name of its own. Always present, always in the same place, where a cell may be scrolled out of view with no usable position
type a valueKeyboard, then verified by looking for the value in the accessibility tree
press a named controllocate.py, which raises the owning window first
open an applicationA fixed list, not an arbitrary command

Run it three ways — and from the panel, which is how it is actually used:

python3 executor.py <trace-dir>          # the plan, no action
python3 executor.py <trace-dir> --run    # actually do it
python3 executor.py <trace-dir> --json   # one event per line, for the panel

Three outcomes, and they are not the same news

The first version halted at the first step it did not recognise, and that made the whole feature inert: the one real recorded lesson opens with "Navigate to the main panel", which is recorder noise, so a run refused at step 1 and never reached the eight substantive steps behind it. The plan said 8 of 17 and the run performed 0.

OutcomeWhat it meansWhat happens next
skippedI do not know how to do thisRecorded as a refusal; the run continues
stepAttempted. ok false means it was tried and could not be confirmedSuccess continues; failure halts
haltedI could do this, but not safely from hereStops, with the reason

taughtThe answer was understoodThe step is performed, and its new wording is saved into the procedure

Skipping is not guessing, and keeping the two apart is the whole design. But skipping is what makes the third outcome necessary.

Never type into a cell you cannot name

Skip "switch to the term 1 sheet" and the next instruction to type lands in whatever sheet happens to be in front — silently, in the right-looking cell of the wrong table. So the cursor's position is tracked: a step that types without naming its cell, after something was skipped, halts instead of typing blind. A goto re-establishes it, and so does a step that names its own cell.

Verification reads the cell

It used to search the accessibility tree for the typed text, which answers a question nobody asked. "Yes" appearing somewhere on screen — in a save dialog's button, say — is not evidence that "Yes" reached I2. A typed value is now read back out of the cell it was typed into, through the Table interface, and compared.

Measured on live Calc — the complete run, 23 Aug 26

All 8 substantive steps performed and verified, 9 noise steps skipped, 34 seconds. I1 read back Exam Eligible, I2 Yes, I4 No – below 65%, I9 Principal – medical certificate — each read from its exact cell over the Table interface, never assumed. The biggest unproven claim in this project is no longer unproven.

An earlier attempt halted on I4 because autocorrect rewrites a spaced hyphen as an en dash. The same rewrite happened to the person who taught the lesson, so verification now compares the autocorrect-folded forms — demanding the raw characters back would fail every lesson taught by a human hand.

How typing actually lands

  • Click first, then type. WM-active and widget-focus are different things: Calc reopens with whatever bar it last showed, and a lingering Find bar holds focus and silently eats every keystroke. The executor clicks just inside the grid's own accessibility rectangle before any key is sent.
  • The Name Box is nameless on this LibreOffice build, so when it cannot be found the executor walks: Ctrl+Home to A1, then arrow keys — I4 is eight Rights and three Downs. Refused beyond 60 columns or 200 rows, where one lost keystroke would land everything one cell off.
  • The grid is never walked. A blank sheet reports 2,147,483,647 children; anything that big is skipped by every name search and its cells reached by row and column instead.

A goto is verifiable now

It used to report "not verifiable, assumed", which was honest and useless. The sheet can be asked which of its cells has focus — through the Collection interface, in one call, without walking a table that reports two billion children. So goto I1 now answers "the cursor is in I1", and arriving in the wrong cell is caught there rather than three steps later when a typed value fails to read back from somewhere it was never written.

These lookups fail intermittently in a long-lived process while Calc sits plainly on screen with the cursor in the right place. That is treated as an unknown, never as a failure: a goto that cannot be confirmed says "arrived, but the sheet would not say where — unverified" and the run continues, because the step after it reads its cell back and does not depend on this at all. Focusing the grid falls back to the window's own geometry for the same reason — a flaky tree query once ended a lesson four steps from the end for no reason a person watching could see.

Ask-when-unsure

A step the executor does not understand no longer just gets skipped — the run pauses and the question appears in the panel's Lessons pane, with a box and two buttons: Tell it and Skip it. The answer travels back as a file in the lesson's own folder (the shared mount is the one channel that crosses the boundary), is re-read by the same understand() that reads every step, and — this is the point — is folded back into procedure.json, so the next run never asks that question again. No answer for three minutes and the step is skipped with that reason; an unattended run cannot hang.

Only while somebody is watching, and at most three times. The panel's Run button asks; a scheduled or headless run does not. The recorded lesson has nine steps it cannot perform, and asking about every one turned a 34-second run into half an hour of a panel waiting on a person who had left. After the third question it goes back to skipping, which is what it did before and is never wrong.

Verified live: a lesson with "Frobnicate the flux register" in the middle asked, was told "Type 'taught mid-run' into cell B2", performed it, verified B2, and finished. The ledger reads like a conversation:

info   lesson.ask     step 2 · Frobnicate the flux register
allow  lesson.answer  step 2 · Type 'taught mid-run' into cell B2
allow  lesson.taught  step 2 · Type 'taught mid-run' into cell B2

Running one from the panel

Lessons are listed, planned and run from the control panel rather than from inside the sandbox, for the same reason everything else is: the path never touches the display, so it survives the evenings when clicking inside the clone does not.

RouteWhat it does
GET /api/lessonsEvery procedure learned, newest first. Read from the host's own copy of shared/, so it still answers when the sandbox is down.
POST /api/lesson/planWhat it would do. Cheap — no display work.
POST /api/lesson/runStarts a run on a background thread. Refuses when the plan can perform nothing at all.

The lesson id names a directory that is interpolated into a shell command inside the sandbox, so it is checked against a character class and against the filesystem — the same rule as the app launcher: a choice from things that exist, never a path.

Every step goes into the ledger, and refusals go in as refusals. lesson.skip and lesson.halt are both deny, kept under separate names because "I did not attempt this" and "I stopped the work" are different events and a log has to say which. In the panel a skip is quiet and a halt is inverted — inversion is the strongest signal this palette has, and nine inverted rows out of seventeen would make a healthy run look like a disaster.

11Findings

Everything else is reactive: you ask, it answers. Findings is the opposite — it reads your spreadsheets and goes looking for what nobody thought to ask about. Six checks, each a bounded brief turned into a program, run, and reported with the program attached so every finding is checkable.

The rule that makes it useful

The first full run was not good enough to show anyone: 8,254 "outliers", sku: 10S reported as a duplicate identifier (it is a pack size), 3,455 items "stopped moving". That is a dump, not a finding.

Every brief now inherits one rule: never more than ten lines, ranked by what makes a thing matter, and say how many there were in total. A finding is only useful if it is short and someone can act on it.

One check is written, not generated

The near-duplicate name check — the one that found the supplier counted twice — reported zero, because the spellings are spread across the ten Purchased From columns and it was grouping each column separately. Told to stack families first, the model then failed twice with increasingly inventive pandas.

So it is written: stack families, normalise case and whitespace, group, keep spellings with at least five rows each, rank by rows affected. 26 findings in two seconds with no model call, against roughly three minutes and two failures before. The app runs a built-in where one exists and generates a program otherwise — the model where the shape varies, code where it does not.

Browsing is a mode you switch on, written to the ledger when it changes, and the sandbox cannot grant it to itself — no sudo, and the rules live outside its reach. Tested: with browsing on, a connection to port 22 was still refused while the web worked.

The claim was never that this can never reach the internet. It is that it cannot unless you say so, and when you do it is in the log.

Read the state you assert, not one it resembles

Both LOCKED and BROWSING are policy drop. Testing only for the policy meant the panel reported LOCKED throughout a two-hour window when the web was open — see §16, the most serious defect this project has had. egress_state() now returns locked only when there is no web rule present, so the three states in the table above are three answers rather than two.

Every deliverable says which it was

A report is stamped with the machine's state at the moment its job started — "Made by Shishya on this machine, with the sandbox's network locked — nothing could leave this computer while this was made. Model: gpt-oss:latest."

Recorded by the host, quoted by the runner. The clone has no sudo and cannot ask nftables anything, so a report claiming its own network was locked would be the sandbox vouching for itself, which is worth nothing. When the state could not be checked it says so rather than guessing. The two hours above are precisely why: those files are indistinguishable from the ones made under lock, and always will be.

Secrets are not mounted

The security model of this project is the mount list, and this applies it to credentials. The store is ~/.shishya/secrets.json, mode 0600, outside the repository — because vm/lima.yaml mounts the whole repo at /opt/shishya, so a secret in var/ is one the clone can read. Tested rather than assumed: a canary written to var/ was read back from inside the sandbox on the first attempt, and a find / across the sandbox for the real store returns nothing.

It is not encrypted, and does not say it is

Encryption needs a key; a key needs either a passphrase typed on every scheduled run, or storage beside the thing it protects — which protects nothing. Claiming "encrypted at rest" while doing the latter is the kind of statement this project exists not to make. What is true: the sandbox has no path to it, the permissions are 0600, and the ledger records that tally.password was set, never what it was set to. An audit trail holding credentials is a place to steal them from.

./demo.sh check verifies both halves on every run — the permissions, and that no stored value has been copied into shared/ by some well-meaning script. Planting a value there turns the check red.

The other three

  • The mount list. The only writable window is shared/. Everything else on the Mac does not exist from inside — and the panel's own file browser is held to the same line, resolving every requested path and refusing anything outside the folder it was given.
  • No sudo. The clone is unprivileged even within its own sandbox.
  • Rollback. APFS clone; 12 seconds; the environment survives and the clone's work does not.

The panel's terminal

Runs inside the sandbox as clone, never on the Mac. Verified: whoami returns clone, sudo -n true demands a password, and ls /Users reports no such directory. Every command is written to the ledger before it runs, so one that hangs still leaves a record of what was asked.

13Design language

Swiss-technical, after a reference the owner supplied: a cool grey gradient ground, pure black hairlines, uppercase letterspaced labels with a great deal of air, square corners, and no colour at all.

Two decisions follow from removing the palette, and both are load-bearing:

  • Emphasis is inversion. A control that is on is a solid black block with white type — the strongest signal available once hue is gone.
  • Refusals in the ledger are inverted blocks, not red rows. The audit trail is the most important thing on the panel, so it gets the strongest treatment the language allows — and unlike colour it survives being photographed, projected badly or printed in mono.

Destructive controls could not be red either, so they are marked structurally: a heavier rule under Roll back, dashed under the reversible pair. A three-state appearance switch (light / dark / auto) sits in the header; auto is the absence of the attribute, which is what the stylesheet already keyed on.

15Known limits

Do not demonstrate
  • Asking it to count or filter across rows in its head. It named two of three students below an attendance threshold, twice out of three runs, and once invented a percentage. Route to code — the shortcut does this automatically, but phrasing that dodges the keywords will slip through.
  • Transcribing an existing table into a spreadsheet. Asked to copy a mark sheet it filled all 48 numeric cells with the word "maths" — a repetition loop under schema-constrained generation. Building a table from prose is fine; copying one is not.
  • A lesson recorded against anything but Calc. Everything below the plan — goto, the cell read-back — is spreadsheet-shaped. A procedure in Writer plans fine and performs nothing.
  • Importing the Tally XML into a real company. The file passes every check that can run here, but Tally itself has never accepted it — that needs a Windows machine. Test company first; Import Data cannot be undone.

Rough edges to know about

  • Scrolling used to blank the screen. Openbox ships four virtual desktops with the mouse wheel over the desktop bound to switching between them, so a scroll that missed a window replaced everything with an empty workspace — indistinguishable, through a video stream, from every app crashing at once. Now one desktop, checked by ./demo.sh check.
  • Clicking inside the sandbox is unreliable. Stale noVNC connections swallow button releases, so windows raise and tooltips show while nothing activates. Drive from the panel; Fix input rebuilds the display in five seconds without closing apps.
  • The VM stops when the Mac sleeps. Every time. ./demo.sh recovers.
  • The egress lock does not survive that restart. nftables rules live in the running kernel and nothing re-applies them at boot, so a sandbox that comes back after the Mac slept comes back open. Found on 3 September by the panel reporting it honestly, which is the only reason it was found at all — the indicator is measured from the guest, so it said OPEN rather than remembering what it had been told. This is the single most testable claim in the project, and a judge asking to see it locked is the likeliest question there is. Until a boot service re-applies it, locking is a step in the pre-flight, not a property of the machine.
  • Ollama is an app and quits. demo.sh restarts it.
  • Filenames uploaded before 21 August are mangled (01_20Retail_20Inventory.xlsx was 01 Retail Inventory.xlsx). The encoding bug is fixed; old files were never renamed.
  • The Telugu answer may be saying something different from the English one. Asked the same question, the English reply opens "does not automatically qualify" and the Telugu opens "అవును" — yes. Both then give the 65–75% band and the 15-day certificate rule, so the substance is there and the emphasis is not the same. Nobody on this project reads Telugu, and a policy answer that leads with the wrong word is exactly the kind of error that matters. Do not demonstrate this until a Telugu speaker has read it.
  • 16 GB is the floor, not 8. Measured, not guessed: the smallest model that answers correctly needs 7.2 GB resident, on top of the sandbox's own allocation and macOS. A 4 GB VM plus that model plus the system is about 16 GB. ./demo.sh does not check this; vm/bench.py measures it.
  • This repository cannot be made public as it stands. shared/training/ holds a real Hyderabad pharmacy's purchase history — 17,011 rows of what they stock and how much of it they buy, month by month. It is in the repository because it was the most useful training material available, which is a completely different bar from "published forever under our names". Two smaller files read badly even though they are synthetic: APP-3307.txt is a welfare application naming Aadhaar among its documents, and class-9b-term1.csv is named students with marks. All three are in history, across 45 commits, so deleting them from the working tree changes nothing — going public exposes every commit. Removing them properly means git filter-repo and a force-push. Private, with read access granted per person, until that is done.
  • There is no hosted demo, and there cannot be one. The mount list in lima.yaml is the security boundary, the model runs on the machine, and the egress lock drops everything outbound. A URL somebody can click and try would mean giving up every one of those — shipping the exact opposite of the claim. The honest answer to "can we try it?" is "yes, on a laptop; if you could try it over the internet it would not be what we are claiming." That is an argument, not an apology.
  • A cloud model is installed — deepseek-v3.1:671b-cloud. Filtered out of the Models picker so it cannot be chosen by accident, but it exists. Selecting it would destroy the entire sovereignty claim.
  • Qt WebEngine needed AppArmor's namespace restriction relaxed inside the VM for the browser to render. A real control loosened, defensible only because the VM is the boundary.
  • An Xvfb can come up with keyboard injection dead. Mouse fine, queries fine, every typed key silently swallowed, for every app. ./demo.sh check now types a probe and reads it back; the cure is the full display-stack restart in ./demo.sh.
  • Raising a window is not focusing it. Anything that types must click its target first — the executor does, and the keyboard check does. A probe that only ran windowactivate reported a failure that was not there.
  • A running process keeps old code until it is restarted — the panel and the desktop shell both. Adding an app to the launcher does not put it in the menu; the shell that draws the menu has to be restarted to read the file. This cost two rounds of "where is my app" in one afternoon. ./demo.sh check now compares each process's start time against its own source and says so; ./demo.sh restarts both.

16The failure ledger

The most valuable section. A design can be re-derived from the code; these cannot. Each cost real time and several were diagnosed wrongly first.

A syntax error stopped the entire panel

Symptom: nothing worked. Every endpoint returned 200, all fourteen checks were green, and the page did nothing.

Cause
The terminal and theme blocks were inserted by anchoring on refresh();, and Python's str.replace replaces every occurrence unless told otherwise. That string appears three times, so the blocks landed inside send() and inside guard()'s finally clause as well, each time leaving an if followed by a const.
Two wrong turns
A bracket counter reported an unclosed parenthesis — it did not know a regex literal from an expression. And the console kept showing the same error after the fix; old messages persist. It was only confirmed by importing the module dynamically.
Lesson
A syntax error is invisible from the outside — every machine-side diagnostic reports perfect health. Check the browser console first when a page misbehaves, and always pass count=1.

The sandbox streamed video of a picture nobody had open

Symptom: none. Everything worked. The machine simply never went idle — a bare desktop with no viewer attached, no job running and nothing on screen sat at a third of a core for as long as it was up.

Cause
The animated wallpaper. It repaints all 1440×900 on a timer, and over VNC a full-screen repaint is a full frame for x11vnc to encode and ship. Nothing connected the drawing to whether anyone could see it, so the desktop generated a video stream into a socket with no reader. Measured at 18.8% of a core in Xvfb plus 13.0% in the shell, permanently.
Two more, found while measuring
The frame-rate setting was never applied — set_live() reset self.fps to 0 on every call, after relabel() had just set it, so a wallpaper configured for 4 fps ran at the built-in 14. And the taskbar tore down and rebuilt every button every two seconds whether or not a window had opened — a 1440×48 repaint forever, four xdotool processes with it, and a churn of the AT-SPI tree the executor grounds on.
Fix
The desktop reads noVNC's own socket out of /proc/net/tcp and stops drawing when the last viewer goes. Three separate gates — a viewer is attached, the model is not thinking, a live wallpaper is chosen — are now all required rather than fighting each other for who spoke last. The taskbar rebuilds only when the window list changes.
Lesson
Work with no observer is still work. On a machine whose screen is watched through a video stream, anything that draws on a timer is a permanent bitrate floor — and a settings value that is silently ignored will never show up as a bug, only as a cost. Prove idleness with pixels: two screenshots seconds apart must be byte-identical.

The VNC server was told not to use the extension that makes it fast

Symptom: none visible. x11vnc ran with -noxdamage for months.

Cause
That flag turns off XDAMAGE, the X extension that reports which rectangles changed, and leaves x11vnc scanning the whole framebuffer on a timer looking for differences itself. xdpyinfo lists DAMAGE on this Xvfb; it works. The flag was defensive and cost real work on every frame.
Alongside it
x11vnc does a reverse DNS lookup on every client that connects. With the egress lock on, that query does not fail — it waits for the resolver to time out, and the screen stays blank for the whole of it. The same failure mode as the sudo hostname lookup already dealt with in provision.sh: the security feature strangling the thing that reports on it. -nolookup.
Why it took months
The display stack was defined inline in provision.sh, which runs exactly once per machine. Changing one flag on one service meant rebuilding the VM — an hour, to test a guess. It is now vm/display.sh, idempotent, re-runnable against a machine that is up, and wired to the panel's Rebuild display button.
Lesson
A defensive flag with no measurement behind it is a permanent tax. And configuration you cannot change without a rebuild will not get changed — the cost of trying is what decides whether anyone ever tries.

Input died three times

Symptom: windows raise, tooltips appear, nothing activates. Looks exactly like a frozen app.

Cause
Stale noVNC connections accumulate — eight websockify children at worst — and button releases stop being delivered. GTK focuses on press and fires on release, so every control took focus and did nothing.
Wrong theories, in order
A GTK bug; window stacking; a stuck mouse button; occlusion. All wrong. What identified it was noticing AT-SPI doAction worked while pointer clicks did not.
Lesson
When a UI looks dead, find a second input path and try it. If one works and the other does not, you have localised the fault in one step.

Rollback wiped the entire sandbox

Symptom: after pressing Roll back, no GTK, no pandas, no apps — every window dead.

Cause
The clean snapshot was taken before the desktop, apps and libraries existed. It did exactly what it was asked and restored a bare Ubuntu.
Lesson
"Undo the work" and "undo everything ever built here" were the same button and nothing said so. A destructive control must name what it will destroy. The confirmation now shows the snapshot's date.

The egress lock strangled the control panel

Symptom: panel bound correctly, listening, timing out on every request.

Cause

Fix
One line: 127.0.1.1 lima-shishya. 10.017s → 0.003s.
Lesson
Locking the network makes everything that quietly expected a network slow rather than broken, and slow is far harder to diagnose.

Confident fabrication on tables

Lesson

It reported nothing was low on stock, across 149 low-stock rows

Four of eight real questions died on the same line

Measurements that lied, three times

What happened

A /proc sample window straddled the moment an answer arrived, so a feature that worked appeared not to.
Lesson
Suspect the instrument before the code. Two of these produced confident wrong reports that had to be retracted.

A search that would have finished in sixteen days

Symptom: with Calc open, every lookup hung. Not slow — nothing ever came back.

Cause
A spreadsheet reports its theoretical size as its child count. Calc says 2,147,483,647, which is INT32_MAX and not a number of cells anyone has. locate.py walked range(childCount) over AT-SPI at roughly 1,500 nodes a second, so descending into one sheet takes about sixteen days.
Fix
A node claiming more children than any real interface has is treated as opaque. 16 days → 1.2 seconds. Nothing findable by name lives in the grid anyway — cells are reached by row and column, not by walking, which is also what made verification possible.
Lesson
A hang and a slow function look identical from outside, and both look like a crash. Ask a tree how big it says it is before walking it, and disbelieve the answer.

The Name Box has no name

Symptom: goto reported "no Name Box — is a spreadsheet open?" with a spreadsheet open.

Cause
LibreOffice exposes the Name Box as an unnamed panel with no text interface. find("Name Box") could never have matched it, in any build. The design note said it was "one control, always present, always in the same place" — right about the screen, wrong about the accessibility tree, and never tested because the search hung before it could return nothing.
Fix
Reached through the toolbar that owns it: Formula Tool Bar is named, and the Name Box is its first panel. Extents are read fresh each time, so moving the window does not break it — which hard-coded coordinates would.
Lesson
A control being obvious on screen says nothing about whether it is reachable. Two bugs in the same path hide each other: the hang concealed the missing name for as long as it existed.

Autocorrect quietly changed the data

Symptom: the run halted on a cell that looked completely right.

Cause
The lesson said No - below 65%. The cell held No – below 65%. LibreOffice replaces a hyphen with an en dash as you type, so what was stored was not what was taught, by one invisible character.
Why this is the good news
The old check searched the screen for the text and would have reported the same failure with no idea why. Reading the cell back said exactly what was in it, so a one-character difference was legible instead of mysterious.
Lesson
The application between you and the file is an editor, not a pipe. Verify by reading back what was stored, never by trusting what was sent — and quote both when they differ.

Refusing correctly, and doing nothing at all

Symptom: the plan said 8 of 17 performable. The run performed 0, and every part of it was working as designed.

Cause
The executor halted at the first step it did not recognise. Step 1 of the only real recorded lesson is "Navigate to the main panel" — recorder noise. It refused at step 1 and never reached the eight substantive steps behind it.
Lesson
"Stop rather than guess" was the right principle applied at the wrong granularity. Not attempting a step and abandoning the job are different refusals, and collapsing them into one made a correct design useless. The distinction cost nothing to add and is the difference between the feature working and not.

The wrong model answered for half an hour

Symptom: "I couldn't write a program for that. Try narrowing it down" — after 30 minutes of thinking.

Cause
Four faults stacked. The chat app never passed a job name, so every call fell back to a 5GB reasoning model while the Models screen showed the 14GB one the owner picked. The context window was a fixed 8,192 while the code path asked for 6,144 tokens of answer, so a 2,700-token file listing left the prompt truncated. The empty-answer retry then doubled the budget inside the same window, making the room for the prompt negative. Both attempts ran to completion: a reasoning model thinking at length, twice, about a question it could not see.
Lesson
A fallback is a decision someone will make by accident — make it the same decision the owner made on purpose. And num_ctx must be sized from the prompt plus the budget, per call, or the retry that "adds room" is taking it away.

Typing did nothing, for three different reasons in one afternoon

Symptom: the executor types, the cell stays empty. Blamed, in order: VNC staleness, AT-SPI, LibreOffice, and Xvfb — one of those was even right once.

Causes, all real
(1) An openbox window menu nobody noticed was open, holding a keyboard grab that ate every key on the display. (2) An Xvfb instance that came up with XTEST keyboard injection dead system-wide — cured only by restarting the display stack. (3) Calc's Find bar, restored from the profile at launch, holding widget focus while the window was active — keys arrived at the window and landed in the search box.
What identified each
A screenshot (the menu was simply visible in it); typing into cat in an xterm and reading the file (empty = X-level, full = app-level); and a single test click into the grid followed by one key, which put an "a" in C5 and ended the argument.
Lesson
When input dies, do not theorise — screenshot first, then type into cat to split X-level from app-level, then click before you type. GTK focuses on press; a window can be active while its grid has no focus at all.

The repair laundered a crash into a deliverable

Symptom: attempt one died with ZeroDivisionError; attempt two delivered a tidy ranked table where every margin was exactly 100%.

Cause
Shown its own traceback, the model "fixed" the division by making the cost vanish — turning a loud failure into confident nonsense with real product names on it, the kind of table that gets screenshotted into a board pack. A separate job invented "placeholder" data outright and said so in its own summary.
Lesson
A retry may only be accepted if it produces more than the attempt it replaces, and a summary confessing dummy or invented data fails the job. Confession in, deliverable out.

The panel read LOCKED for two hours while the sandbox could reach GitHub

Symptom: none, until something tested it. The header said EGRESS · LOCKED, nftables agreed, and curl https://github.com from inside the sandbox returned 200.

Cause
egress_state() decided the answer by testing for policy drop in the ruleset. Browsing mode is also policy drop — with DNS and 80/443 punched through it. The two states are indistinguishable by that test, so the moment browsing was switched on for an apt install, the indicator went on reporting LOCKED and never stopped.
How long
Browsing was granted at 16:14:45 and left on. Every deliverable made in the following two hours was produced on a machine that could reach the internet, and not one of them recorded that.
Lesson
This is the project's whole claim, and it was wrong in the safest-looking way: an indicator that was measuring something, just not the thing it named. An indicator must test for the state it asserts, not for a condition that state happens to share with another. Locked now means the model and nothing else; browsing reports as browsing, in both readouts. Found by ./demo.sh rehearse on its first run, which is the entire argument for that command existing.

A setting that was written, accepted, and silently discarded

Symptom: AutoCorrect kept turning a typed hyphen into an en dash after being switched off. The keys were in the profile — grep found them — and LibreOffice ignored them.

Cause
The property name was guessed. The real one is ChangeDash, not ReplaceDashes; the path /org.openoffice.Office.Common/AutoCorrect had been right all along. LibreOffice validates the profile against its schema and drops items for properties that do not exist, without complaint, so the file looked correct right up until the moment it was reloaded.
What found it
Grepping share/registry/main.xcd — the schema ships with the application and names every property it will accept. The answer was on disk the entire time.
Lesson
When a configuration is written and ignored, read the schema rather than guessing again. A setting that is accepted and discarded looks exactly like a setting that is applied — and a second guess is no more likely than the first.

A whole layer of the interface was invisible and nobody noticed

Symptom: none. The panel looked clean, and had looked clean for weeks.

Cause
Every section label, the ledger's column captions and both corner marks were --ink-4 on the grey ground — 1.35:1 in the light theme, against 4.5:1 for text and 3:1 for large text. They were being drawn and could not be read. It surfaced only when the theme was switched to light for a screenshot and the words were simply not there.
Lesson
Measure the greys, do not choose them. A restrained palette hides this failure better than a loud one: nothing looks wrong, because the thing that is wrong is not visible. Check both themes at the worst point of any gradient, and prefer the arithmetic to the eye.

A window with nothing in it, and no error anywhere

Symptom: the Billing app opened as a blank white rectangle. Empty log, clean exit code, process alive, accessibility tree reporting a frame with zero children.

Cause
The class is a Gtk.Window, and it defined a method called add() — for adding a product to the bill. Gtk.Container already defines add(). So self.add(root) in the constructor called the billing method with the root box as a product id, found no such product, and returned. The window was never given its contents, and nothing anywhere failed.
Lesson
Never name a method after the toolkit's. Subclassing hands you every name the parent owns, and shadowing one fails silently by doing something perfectly reasonable with the wrong argument. When a window is blank and the log is clean, count the accessible children before theorising.

The search results could not be pressed

Symptom: the counter looked right, searched correctly, and could not be driven — every attempt to add a product silently did nothing.

Cause
Results were GtkListBoxRows. A row publishes no action to AT-SPI, so there is nothing to invoke: a person can click it and nothing else can. In a project where every app must be drivable from the panel and teachable by demonstration, that is the same as not working.
Lesson
If a control cannot be operated through the accessibility layer, it does not exist to this system. A flat Gtk.Button looks identical to a row and can be pressed — build for the tree, not only for the eye.

Smaller ones worth not repeating

  • {{.Dir}} in Lima is the instance directory, not the config file's — both mounts pointed at the wrong place.
  • useradd -m leaves the home root-owned when the directory already exists as a mount parent.
  • pkill -f "shell/desktop.py" never matched because provisioning cds first — four desktops stacked up unnoticed.
  • int(1000 / self.fps or fps) parses as (1000 / self.fps) or fps — divides by zero instead of falling back.
  • self.boxes initialised after the loop that fills it — desktop crashed with every icon missing.
  • The upload handler never decoded the percent-encoded filename, mangling every file with a space in its name.
  • Backgrounding through limactl shell never detaches cleanly; use a systemd unit or setsid with stdin closed.
  • A range-replacement between two markers deleted a function; Python still parsed and the app caught the error per click.
  • The ledger rendered 94 entries into zero height — a flex child with no min-height. It was rendering into nothing, which looks identical to not rendering. It then happened again, in the same stylesheet, to the pane that shows a lesson plan: seventeen rows into twenty-six pixels. Fixing one instance of a trap does not fix the trap.
  • A GTK stylesheet is a bytes literal; an em dash in a comment breaks the whole shell.
  • Binding only to 127.0.0.1 means localhost fails, because macOS resolves it to ::1 first.
  • A blank Calc sheet reports INT_MAX accessible children — walking it is why finding the Name Box used to take forever. Grids are skipped by name walks and read by row and column.
  • A notes reader capped at two files silently never read the third notes file anyone wrote. Budget by size, never by count.
  • A prompt-size budget that dropped whole files dropped the largest workbook — the only one that could answer — while keeping four small files nobody asked about. Trim detail, never drop the path.
  • pkill -f with a literal pattern killed the probe that contained the pattern in its own command line. Build the match string at runtime.
  • ROLES was already the job→model map in common.py; a second ROLES for clerk/head shadowed it and handed set_role a Path. Two different things cannot share a name in one module, and the one defined later wins silently.
  • A test that built three bill numbers from the clock in the same second gave all three the same number, and a void reported the wrong bill as already voided. The bug was in the test; the code was right. Timestamps are not identifiers.
  • Openbox reads its desktop count at startup but honours one already set on the root window, so restarting the window manager alone does not reduce four desktops to one while Xvfb is still up. xdotool set_num_desktops changes the live session without touching a window.
  • An app added to desktop.py is not in the menu until the desktop shell restarts. Twice: Reports, then Billing. The file was right both times, which is exactly why it was confusing — the source and the screen disagreed and nothing reported it.
  • macOS ps has no etimes, so a process-age check written for Linux prints the keyword list and compares an empty string. The host half of that check is Python for this reason.
  • The recorded lesson types the value into a cell a goto selected, so the type step carries no cell name of its own — the executor fills it in from the goto, or the retry would overwrite whatever Return moved to.

18Demonstrating it

Twenty minutes before, not five

Twenty, so there is room to fix whatever the checks find. Five only tells you that you are about to have a bad time.

  1. ./demo.sh check — 24 lines, about a minute. Everything must be green. It types a key into a real window and reads it back, compares each running process against its own source, and reads the egress lock from the guest rather than from memory.
  2. ./demo.sh rehearse — every claim you are about to make, exercised, before an audience exists.
  3. Lock egress by hand. It does not survive the restart the sleeping Mac caused (§15). The panel will tell you the truth; believe it over your memory of having locked it yesterday.
  4. caffeinate. If the Mac sleeps mid-call the sandbox stops, and recovery is minutes with people watching.
  5. Confirm a model is resident. The check says so. Cold, the first question costs 16.4 seconds of silence before its first word.
Presenting over a video call

You are screen-sharing a video stream of a screen, and the encoder on the far end spends its bits on whatever moves. The animated wallpaper moves across all 1440×900, continuously — so the spreadsheet numbers somebody is squinting at are precisely what gets sacrificed to pay for it.

Set the wallpaper to a plain colour for the call (Settings, in the sandbox). Measured: 18.7% of a core down to 1.3%, and more to the point the screen becomes still except where work is actually happening. Switch it back afterwards.

The six minutes

  1. Open on the problem, not the product. Staff paste confidential records into cloud AI; once it leaves the building you cannot control or audit it.
  2. Drop their own documents on the panel and press Use as sources. The chat notices and says what it read.
  3. Ask a question they actually get asked. Then let them choose the next one — that is what stops it reading as rehearsed.
  4. Ask for something counted — it writes a program and shows it. Say plainly that it is unreliable at arithmetic by eye, which is exactly why it writes code.
  5. Run Findings. The duplicate-supplier result is the strongest thing this project does.
  6. Ask it to make a document and open the file.
  7. Teach it something, then press Plan. The plan is the honest part: it says how much of what you showed it it can actually do, before it does any of it. Then Run, and watch the steps land one at a time.
  8. Prove the network claim. Point at the egress readout, then curl from inside the sandbox and watch it return nothing while the model keeps answering.
  9. Open the ledger and point at the inverted refusal line.
  10. Roll back and watch the last ten minutes cease to exist.
If something fails live

Own it immediately: "That is wrong, and this is exactly why the log and the undo button exist." Then show the source it read. The audience is judging whether you are honest about limitations, and a demonstration that goes perfectly teaches them less about you than one that does not.

19What to build next

What this is, said the other way round

Worth settling before any of the work below, because it changes what gets built rather than only what gets said.

Counted honestly, this is already about eighty per cent of an ERP. An ERP core is inventory, sales, invoicing, receivables, reporting, an audit trail and roles. There is a catalogue with cost, price and stock; a billing counter; GST tax invoices broken out by rate; void and returns; customers and khata; a stock audit against reorder points; margin and month-sales reporting; scheduled runs; alerts; backups; clerk and head with approvals between them; a Tally round trip; and an append-only ledger of every action and every refusal. Tally does not have half of that, and Tally is what these shops actually use.

So the question was never whether to build an ERP. It is whether to say ERP — and the answer is yes, with one condition that matters more than the reframing.

"An ERP for a shop that cannot afford one" places itself in a sentence, names its buyer, and names the incumbent it should be measured against. Six minutes is not long enough to make someone work for that. But an AI dashboard is the most common project at any hackathon in the world, and a pitch that leads with the dashboard is competing with forty teams who wired a chart library to a language model. What almost nobody has is the rest of it: it learns a procedure by being shown once, in a real GUI, then performs it — and afterwards you can prove exactly what it did and what it was refused.

The ERP is the demonstration. Learning by demonstration, and the ledger, are the claim. Lead with the shop because it is concrete; the moment there is attention, teach it something live and let it do the thing.

"Personalised" is already true and should be said plainly. It does not learn shops in general. It learns this one — the lessons in shared/lessons/ are the personalisation, and they are per-machine by construction.

The one piece of new interface that earns its place is a single overview screen: today's takings and margin, stock at its reorder point, what is owed, what is scheduled, what is waiting on a person. Every one of those numbers already exists — they are scattered across Billing, Reports, Alerts and the panel. Gathering them is half a day and it is what "ERP" looks like in the first fifteen seconds of a video call. Purchase orders, the supplier side and a real profit-and-loss are genuine ERP scope and genuine weeks. Not with a screening pending.

21Working on this from Windows

Written when a second developer joined on a Windows machine. The honest summary is that half of this runs there and half of it cannot, and being clear about which half is worth more than any amount of shimming.

What cannot run, and why not

The sandbox is Lima, which is macOS and Linux and has no Windows build. Everything inside it goes with it: the virtual display, the GTK apps, the recorder, the executor, the accessibility tree they ground on, and the nftables egress lock. APFS copy-on-write snapshots — the undo button — are macOS and a filesystem, not a program. _clone() now says exactly that rather than raising a FileNotFoundError naming cp, which reads like a broken install rather than a platform that does not have the filesystem this depends on.

WSL2 with Ubuntu is the real path to the whole thing, and it is weeks rather than an afternoon: host/vm.py shells out to limactl in about twenty places, and under WSL you would be driving the distribution itself rather than a VM inside it. Nested virtualisation under WSL exists and is not something to stake a demonstration on.

What does run, which is where most of the work is

The shop's books, GST invoicing, the Tally round trip, the task and experiment records, the secret store, the ledger, and the entire control-panel front end. serve.py starts and reports limactl not installed rather than falling over, so the panel loads and every part of it that does not need the VM works. python doctor.py — standard library only, no bash — reports all of this for the machine it is run on, and is the first thing to run after cloning.

The one that actually bit

Windows defaults text files to cp1252, not UTF-8. Every price in this system carries a ₹, half the comments are in three scripts, and host/tasks.py wrote its store with json.dumps(…, ensure_ascii=False) — raw non-ASCII — through a write_text() that named no encoding. On macOS the locale is UTF-8 and it worked; on Windows that is a UnicodeEncodeError in the middle of saving a bill.

Eighty-four calls across twenty-nine files were reading and writing text at the mercy of whatever locale the machine happened to have. They all name encoding="utf-8" now. Found with the AST rather than a regex, because write_text(json.dumps(rows, indent=2, ensure_ascii=False)) has nested parentheses and commas and the encoding belongs on the outer call — a regex gets that wrong in a way that still parses.

The failure is invisible on the machine most of this was written on. That is what makes it worth a check rather than a convention: doctor.py walks the AST and fails if any text read or write has stopped naming its encoding.

The boundary was one laptop's

Found while making the above work. vm/lima.yaml's mount list is the security boundary — and it wrote out one developer's home directory in full, so it described a boundary that existed on exactly one machine. Anyone else who cloned the repository got a sandbox mounting a path that was not there. It is a template now, carrying __SHISHYA_ROOT__, resolved against the checkout into var/ at creation time, which is why first boot is vm.create() and no longer limactl start … vm/lima.yaml.

host_online() went the same way. It asked route -n get default, which is BSD and answered only on macOS — everywhere else browsing was refused on a machine that was perfectly online. It opens a UDP socket toward a public address instead, which assigns a local route without sending a packet: the same question, portably.

Where to start

  1. python doctor.py. It will tell you what your machine can do before you have formed an opinion about it.
  2. vm/shell/books.py is the best first file. It owns the schema and is the only writer to it, the arithmetic is worth being exact about, and none of it needs a VM.
  3. web/ is plain ES modules and CSS with no build step. Edit, reload, done.
  4. The overview screen in §19 is the piece most worth having and is almost entirely front end.
